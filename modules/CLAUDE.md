# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is the **BV-BRC dev_container modules directory** - a collection of bioinformatics modules for the BV-BRC (Bacterial and Viral Bioinformatics Resource Center) project. The dev container is a build system that wraps multiple GitHub repositories (modules) and provides unified development and deployment infrastructure.

**Primary languages**: Perl, Python, Shell scripts, with some Go, Java, and C++

## Build Commands

```bash
# From the dev_container root (parent directory)
./checkout-bvbrc-modules        # Clone all core modules (first time setup)
./bootstrap /path/to/runtime    # Initial setup (links to runtime, creates user-env.sh)
source user-env.sh              # REQUIRED before any make commands
make                            # Build all modules
make test                       # Run tests for all modules
make deploy TARGET=/kb/deployment  # Deploy to production directory

# Build a single module
cd modules/<module_name> && make

# Clean rebuild
rm bin/* && make

# If bootstrap reports missing dependencies, use:
KB_IGNORE_MISSING_DEPENDENCIES=1 ./bootstrap /path/to/runtime
```

After adding new modules to `modules/`, run `./bootstrap` again and re-source `user-env.sh`.

## Architecture

### Dev Container Structure

```
dev_container/
├── modules/          # Git repositories for each component
├── bin/              # Wrapped executables (generated)
├── tools/            # Build infrastructure (Makefile.common, wrap_* scripts)
├── runtime -> ...    # Symlink to runtime (perl, python, third-party tools)
├── user-env.sh       # Environment setup (generated by bootstrap)
└── Makefile          # Top-level build orchestration
```

### Module Structure

Each module follows this pattern:
- `scripts/*.pl|py|sh|R` - User-facing scripts (wrapped to `bin/`)
- `service-scripts/` - Service-specific scripts
- `lib/` - Perl/Python libraries (added to library paths)
- `app_specs/*.json` - Application specifications for BV-BRC job submission
- `Makefile` - Module-specific build rules (includes `tools/Makefile.common`)
- `*.spec` - TypeSpec API definitions (for JSONRPC services)

### Core Modules

| Module | Purpose |
|--------|---------|
| `p3_auth` | Authentication support |
| `app_service` | Application submission queue (Slurm scheduler integration, port 7124) |
| `p3_cli` | Command-line interface scripts (Perl) |
| `p3_core` | Common core libraries |
| `Workspace` | User file/object storage service (MongoDB + Shock, port 7125) |
| `typecomp` | RPC type compiler for generating clients from .spec files |
| `BV-BRC-Go-SDK` | Go SDK and CLI tools (Go reimplementation of p3_cli) |
| `genome_annotation` | Genome annotation service (port 7050) |
| `sra_cache_service` | SRA precaching + toolkit access (JSONRPC, Go; ports 7141/7142) |

### JSONRPC Services

Services use the TypeSpec pattern:
1. API defined in `*.spec` file (e.g., `Workspace.spec`, `AppService.spec`)
2. `make compile-typespec` generates clients (Perl, Python, JavaScript)
3. Implementation in `*Impl.pm` or `*Impl.py` (hand-written)
4. Generated `*Client.pm` files - **never edit directly**

### Script Wrapping

Scripts are not run directly. The build system creates wrappers in `bin/` that set up the environment:
- `scripts/foo.pl` → `bin/foo` (Perl wrapper via `wrap_perl.sh`)
- `scripts/bar.py` → `bin/bar` (Python3 wrapper via `wrap_python3.sh`)
- `scripts/baz.sh` → `bin/baz` (Shell wrapper via `wrap_sh.sh`)
- `scripts/qux.R` → `bin/qux` (R wrapper via `wrap_rscript.sh`)

Run scripts via their wrapper name without extension: `foo` not `foo.pl`

Set `KB_INTERACTIVE=1` when running scripts interactively.

## Key Patterns

### Adding Scripts

1. Place script in `scripts/` (user-facing) or `service-scripts/` (service-specific)
2. Run `make` in the module directory
3. Wrapper appears in `$KB_TOP/bin/`

### Adding API Methods (for services)

1. Define in `*.spec` file with authentication requirements
2. Implement in `*Impl.pm` or `*Impl.py`
3. Run `make compile-typespec` in the module directory
4. Add tests

### Environment Variables

- `KB_TOP` - Dev container root
- `KB_RUNTIME` - Path to runtime (perl, python, etc.)
- `KB_PERL_PATH` / `PERL5LIB` - Perl library paths
- `KB_DEPLOYMENT_CONFIG` - Path to service configuration
- `P3_USER_AGENT` - Override the client User-Agent (see HTTP diagnostics below)
- `P3_DEBUG_HTTP` - Dump headers of failed HTTP exchanges (Perl **and** Go)

## HTTP diagnostics / Cloudflare (2026-08, revised 2026-10-19)

The BV-BRC web sites sit behind Cloudflare, which rejects disallowed library
user-agents with **error 1010** before the request ever reaches the origin.
Clients used to report nothing but a status code, so an edge rejection was
indistinguishable from a bad password.

> **The target is an allowlist, and that inverts the whole problem.** The
> agreement with the Cloudflare administrator is that BV-BRC traffic is
> identified by a **`bvbrc-*`** user agent and a rule *admits that family*.
> Everything below that reads "the 1010 rule is a block-list, not an allowlist"
> describes the **current** configuration, not the target one.
>
> The consequence is easy to get backwards: under an allowlist **`BV-BRC P3
> Client` fails** — there is no `bvbrc` substring in it — so the string that has
> been our safe agent for two years becomes the unsafe one the day the rule
> changes. Every identity must start `bvbrc-`.
>
> **Measuring the live edge cannot show you this.** As of 2026-10-19 an
> arbitrary string (`xyzzy`) still gets **200** from `www.patricbrc.org/api`;
> only known library agents are refused. A measurement-led review will
> therefore conclude the work is cosmetic. It is not — it is runway.

- **`P3_DEBUG_HTTP=1` is the cross-language switch.** Set it and any failing
  HTTP exchange in the Perl clients *or* the Go SDK prints a redacted dump of
  the request/response headers plus ≤2 KiB of body. It needs no per-command
  plumbing, so it works across every `p3-*` tool in both trees. `p3-login`
  (both languages) also takes `--debug-http`; the Go `--debug` data-option flag
  enables it too.
- **Never printed:** `Authorization` / `Cookie` / `Set-Cookie` /
  `Proxy-Authorization` / `X-Auth-Token` values (shown as `<redacted, N bytes>`)
  and the **request body** — the login POST body is the user's password, and
  `login_rast` puts the password in a Basic `Authorization` header. Both test
  suites assert the password, the base64 Basic credential and a cookie value
  are all absent from a dump.
- **The Perl UA default moved off `libwww-perl` — but only partly, and only on
  some masters.** An earlier version of this file said "all now build their
  agent with `P3ClientUA::new_ua()`". **That was never true.** Checked per
  module on each upstream master, 2026-10-19:

  | module | state on master |
  |---|---|
  | `p3_auth` `P3AuthLogin`, `P3TokenValidator` | fixed |
  | `p3_core` `P3Utils` | fixed |
  | `p3_core` `P3DataAPI` | fixed, bar one bare UA at `:2274` → `http://spruce:6100/lookup`, an internal non-CF host (one of the unused experiment endpoints) |
  | `p3_cli` `P3WorkspaceClient`, `RASTlib` | **3 bare `LWP::UserAgent->new()` each, no `P3ClientUA` at all** |

  The p3_cli fix (`de04c9a`) was written in August and sat unmerged on a local
  branch, so the Perl CLI has been sending `libwww-perl` the whole time. The
  full sweep found **23 leak sites across four repositories**; see the PR list
  below.
- **UA precedence (revised 2026-08-18) — this is PR#9's order, not master's.**
  On the branch: `$ENV{P3_USER_AGENT}` → **product identity** →
  `$FIG_Config::p3_data_api_user_agent` → `"bvbrc-client-perl"`. **On
  `bvbrc/master` today** `user_agent_string` is still
  `$configured || $ENV{P3_USER_AGENT} || $default_user_agent`, with no product
  step and `$default_user_agent = "BV-BRC P3 Client"` (`P3ClientUA.pm:20`) —
  so until p3_auth#9 merges, the fallback is the *old* string and
  `P3_USER_AGENT` is still outranked by FIG_Config.
  The original order had FIG_Config first, which made the other two dead code:
  `p3_data_api_user_agent` is set (to the stock string) in **every** deployment
  by `p3_seedtk/FIG_Config.pm.tt:50`, so `P3_USER_AGENT=…` appeared to do
  nothing. Read FIG_Config as "the site default for clients that have no
  identity of their own".
- **Product identity — how a client says which product it is.**
  `P3ClientUA::set_product($name, $version)` in-process, or
  **`P3_CLIENT_PRODUCT`** in the environment (whole string); an explicit
  `set_product` beats an inherited env value. Rendered `name/version`, or a bare
  `name` when no version is supplied.
  - **None of this was merged until now, despite what this file used to say.**
    It claimed "two products are declared today". In fact `set_product` existed
    only as a single unpushed local commit on `p3_auth`
    `feature/client-product-identity`, while `p3_cli`'s `Makefile` exported
    `P3_CLIENT_PRODUCT` for a reader that was not on any master — a producer
    with no consumer. The resolved agent was always the fallback.
  - **Four products, all in review as of 2026-10-19:** `bvbrc-cli-perl`
    (p3_cli), `bvbrc-auth-perl` (p3_auth), `bvbrc-app-perl` (app_service),
    `bvbrc-sas-perl/1.039` (seed_core `ClientThing`), over the generic fallback
    `bvbrc-client-perl`. Go side already complies: `bvbrc-cli-go`,
    `bvbrc-auth-go`, `bvbrc-go-sdk`.
  - **`bvbrc-app-perl` is declared in `AppScript.pm`, not a Makefile** — the
    one place the p3_cli wrapper trick is *not* needed, because **all 50
    `App-*.pl` across 36 repositories load `AppScript`** (re-counted
    2026-10-20; it was 47/33 when this was written, and the misses are still
    zero). Note two of them are not where you would look: `sra_import`'s is at
    the repo top level rather than in `service-scripts/`, and `codon_trees`
    contains two nested repos with their own. One line covers them
    all, and an app script run directly still has an identity. The
    `set_product`-beats-inherited-env rule is load-bearing there: an app
    launched by a `p3-*` tool inherits `bvbrc-cli-perl` and would otherwise
    claim to be the CLI.
  - **Guard the call with `->can`.** It runs at module load in all 47 app
    scripts, and `app_service`/`p3_auth` deploy independently, so an undefined
    `set_product` would not degrade the agent — it would kill every app at
    startup, exactly as `p3_core` did for three weeks with `retry_request`.
  - **The seam is the generated wrapper, not the source.** Each module's
    `Makefile` sets `P3_CLIENT_PRODUCT` and puts it in `WRAP_VARIABLES`, so
    `tools/wrap_perl.sh` bakes an `export` into every `bin/p3-*`. That is the
    only seam covering all of p3_cli — there is no module its 137 scripts all
    load, and the HTTP clients that talk to the API (`P3DataAPI`, `P3Utils`)
    live in **p3_core**, so putting it there would mislabel non-CLI callers.
  - Consequences of it being an env var: a script run **directly** (not via its
    wrapper) has no identity, and a child process **inherits** the parent's —
    except where the child is itself a wrapper, which re-exports and so wins
    (`p3-login` invoked from a p3_cli tool correctly says `bvbrc-auth-perl`).
  - **The version is deliberately absent from the source tree** — stamping is a
    release-tooling job, mirroring the Go SDK's `-ldflags -X …version.Version`.
    `make P3_CLI_VERSION=1.2.3` → `bvbrc-cli-perl/1.2.3`,
    `make P3_AUTH_VERSION=1.2.3` → `bvbrc-auth-perl/1.2.3`; plain `make` gives
    the bare name. Nothing guesses a version.
  - **The wrappers must depend on the Makefile** (`$(BIN_PERL): Makefile`) or an
    existing tree keeps announcing the old identity until someone empties
    `bin/`. Put that rule **after** the `all:` target — as the first rule in the
    file it silently becomes make's default goal.
  - Verified live 2026-08-18: `bvbrc-cli-perl` and `bvbrc-cli-perl/1.2.3` both
    get **200** from `www.patricbrc.org/api` (`libwww-perl` gets 403), and
    `bvbrc-auth-perl` gets a plain **401** from `user.patricbrc.org/authenticate`
    (i.e. reaches the origin). So the 1010 rule **as currently configured** is a
    block-list of known library agents, not an allowlist — see the allowlist
    note at the top of this section for why that is the transitional state and
    not the thing to design against.
  - **Where the two non-obvious strings live, if you are hunting them:** the
    fallback is `p3_auth/lib/P3ClientUA.pm:20` `$default_user_agent`, and the
    deployment-wide default is `p3_seedtk/Makefile:22` `DATA_API_USER_AGENT` →
    `$FIG_Config::p3_data_api_user_agent` (`FIG_Config.pm.tt:50`). **Both are
    still literally `"BV-BRC P3 Client"` on master** — neither has moved to a
    `bvbrc-*` name yet; that is what p3_auth#9 and p3_seedtk#1 do, which is why
    they must land together. **The second outranks the first and is set in
    every deployment**, so fixing only `P3ClientUA` changes nothing in
    production while every test still passes.
- **`P3ClientUA` lives in `p3_auth`, not `p3_core`**, purely for dependency
  ordering: `p3_core` depends on `p3_auth` (`P3AuthToken`), never the reverse,
  so `p3_auth` is the only module all three (`p3_auth`/`p3_core`/`p3_cli`) can
  import from. Do **not** fold it into `P3AuthConstants.pm` — that file is
  generated from `Constants.pm.tt`. Go equivalent: `internal/httpdiag`.
- **Three wire forms of the same 1010** — all observed live, all must be
  detected. (1) an **HTML** error page (`Error 1010`, `cf-error-details`);
  (2) **JSON** (`{"error_code":1010,…,"cloudflare_error":true,"retryable":false}`),
  which is what `www.patricbrc.org/api` serves a JSON-requesting client; (3) a
  bare **`text/plain`** body `error code: 1010` (17 bytes), served to the Perl
  solr query path. The colon in form 3 is why the matcher is
  `Error\s+(?:code)?\s*:?\s*10\d\d` and not something tighter.
- **A `CF-Ray` header is not evidence of a block.** Cloudflare stamps it on
  everything it proxies, including an ordinary 401 from our login service — key
  a block off `CF-Mitigated`, a body marker, or a CF-generated status served as
  `text/html`. The Ray id is always reported (support asks for it) but
  "blocked by Cloudflare" only when warranted.
- **Where the rule actually is:** `www.patricbrc.org/api` returns **403** to
  `libwww-perl` and 200 to the allowlisted string, but
  `user.patricbrc.org/authenticate` returns 401 to `libwww-perl`,
  `BV-BRC P3 Client` and `Go-http-client/1.1` alike — so as of 2026-08 the 1010
  rule is on the **patricbrc www zone, not the auth endpoint**. The login-path
  UA fix is prophylactic; the diagnostics are what will identify an intermittent
  rejection. Narrower still: **`www.bv-brc.org/api` serves `libwww-perl` a 200**
  (measured 2026-08-18, still true 2026-10-19) — and that is `P3DataAPI`'s
  *default* url, so a plain `p3-*` query never reproduces a block. Reproduce by
  passing the patricbrc url explicitly:
  `P3DataAPI->new("https://www.patricbrc.org/api")`.
- **The rule has widened since August, and reaches the nmpdr zones too**
  (measured 2026-10-19). `libwww-perl` now gets **403 `error code: 1010`** from
  `www.patricbrc.org/api`, `patricbrc.org/api`, **`www.bv-brc.org/` (root — did
  not block in August)**, **`alpha.bv-brc.org/api` (new)**, and both
  **`servers.nmpdr.org`** and **`rast.nmpdr.org`**. The nmpdr pair matters
  because it means the legacy SEED server family (`SAPserver`, `RASTserver`,
  `ANNOserver`, `ATserver`, `ALITREserver`, all via `seed_core/ClientThing.pm`)
  is subject to the same policy — hence `bvbrc-sas-perl/1.039`.
  **`p3.theseed.org` is not behind Cloudflare at all** (direct A record,
  `Server: nginx`, no `cf-ray`), so Workspace/AppService JSONRPC traffic never
  meets this rule.
- **The nine PRs doing the `bvbrc-*` migration** (all open, 2026-10-19;
  `p3_auth` and `p3_seedtk` must land together and first, the rest are
  order-independent):
  BV-BRC/p3_auth#9 (`set_product`, precedence, fallback) ·
  BV-BRC/p3_seedtk#1 (deployment default) · BV-BRC/p3_cli#24 ·
  BV-BRC/app_service#40 · BV-BRC/Workspace#105 · TheSEED/typecomp#5 ·
  TheSEED/seed_core#2 · BV-BRC/p3_minhash#13 · TheSEED/genome_annotation#35.
  Known gap left out on purpose: `sra_cache_service`'s tracked
  `SRACacheClient.pm` — pre-deployment, with three unmerged branches in flight,
  so it belongs to that module's Phase 10.
- **Generated JSONRPC clients were a second, separate source of the leak.**
  All three typecomp templates emitted a non-conforming agent: `p3_client_stub.tt`
  built a bare UA *and* overwrote the agent with `"<Package> UserAgent"`,
  `simple_client_stub.tt` built a bare UA and set nothing, and `client_stub.tt`
  set no agent at all (inheriting `JSON::RPC::Legacy::Client`'s). Fixing the
  template only reaches the **untracked** generated clients, which are rebuilt
  at build time; **three are tracked** (`Workspace`, `genome_annotation`,
  `p3_minhash`) and needed their own change.
  - Workspace regenerated cleanly — the diff was exactly the template change.
    The other two **have drifted from their own `.spec`**, so regenerating
    dragged in a large unrelated catch-up diff plus `Impl`/`Service` rewrites;
    there the four lines were applied by hand instead. That is the one case
    where editing a generated client is right: the template now produces the
    same thing, so a later regeneration reproduces rather than reverts it.
  - **`p3_cli/lib/P3WorkspaceClient.pm` is vendored, not generated** — p3_cli
    has no `.spec` and no `compile_typespec` target. The template fix does not
    reach it; it must be patched in place.
- **Known wart (not fixed):** `P3DataAPI`'s query loop retries a 1010 fifteen
  times with growing sleeps (~135 s) even though Cloudflare marks it
  `"retryable":false`. `solr_query_raw` dies immediately and is the fast way to
  reproduce a block.

### Test Directory Conventions

- `t/server-tests/` - Tests requiring running service dependencies
- `t/script-tests/` - Tests for command-line scripts
- `t/prod-tests/` - Production environment tests
- `tests/` - Python/other test directories

Most service tests require running dependencies (MongoDB, Shock, etc.) configured in `test.cfg` or `deploy.cfg`.

### App QA fixtures (`tests/*.json`) — two locations + private-workspace pitfall

App submit params for the QA harness live as JSON fixtures in **two** places
that must be kept in sync:
- **In the module repo:** `<module>/tests/*.json` (source of truth, version-controlled).
- **On the QA host:** `/vol/patric3/QA/applications/App-<Name>/tests/*.json` —
  **this is what `p3x-run-qa-suite` actually reads.** Editing the repo copy alone
  does **not** change what the QA run executes; copy the corrected fixtures to
  `/vol` too (the dir is writable by the QA owner). Snapshots of the `/vol` copy
  live under `/vol/patric3/.snapshot/daily.<date>/QA/applications/App-<Name>/tests/`
  — useful for recovering edits that were made on `/vol` but never committed back.

- **Pitfall — fixtures referencing a private workspace.** Many legacy fixtures
  point `output_path` / input file paths (`fasta_files[].file`, `alignment_file`,
  `group_file`, feature/genome group refs, …) at some other user's **private**
  workspace (e.g. `/jsporter@patricbrc.org/home/...`, `/…/JSP_debug/<user>/…`).
  The QA runner can't read those, so `$ws->stat($path)` returns `undef` at
  preflight — and an app that calls `->size` on the result without guarding
  **crashes** (opaque JSONRPC `-32603`) instead of failing cleanly. Fix at both
  ends: guard `stat` in the app's `preflight` (die with the offending path), and
  repoint fixtures at an **accessible** QA area
  (`/olson@patricbrc.org/PATRIC-QA/applications/App-<Name>/`). Globally-readable
  shared data (e.g. `/BVBRC@patricbrc.org/BVBRC Tests/…`) is fine as-is.
- **`p3-cp -A` / `p3-ls -A` (hidden admin flag, not in `--help`).** To copy data
  out of another user's private workspace into an accessible QA dir, use
  `p3-cp -A -f ws:/<owner>@patricbrc.org/… ws:/olson@patricbrc.org/PATRIC-QA/applications/App-<Name>/`.
  `-A` (admin) bypasses the read-permission wall; object **type is preserved**
  (a `feature_group` stays a `feature_group`, not flattened to a file). `p3-ls -A`
  likewise lets you inspect/stat private paths.
- **Verify before running:** `grep -l jsporter tests/*.json` should return nothing,
  and every referenced input must resolve as the running user (`p3-ls` without
  `-A`). Applied 2026-07 to `p3_msa` and `bvbrc_metacats` (see Module Notes).
- **`p3-ls` exits 0 on a missing path**, printing `<path>: Object not found` on
  **stderr** — so `p3-ls "$p" >/dev/null 2>&1` is always true and is not an
  existence test. Test the output instead: `p3-ls -d` echoes the path on stdout
  when it exists and prints nothing there when it does not, i.e.
  `[[ -n $(p3-ls -d "$p" 2>/dev/null) ]]`.

## Module Notes

### app_service (scheduler API)

The scheduler queue lives in a MySQL DB (`sched_db_*` config). Two access styles
coexist: **local DB tools** in `service-scripts/` (`p3x-qstat.pl` connects
directly via `DBI`, host-bound) and the **JSONRPC API** in `AppService.spec` +
`lib/Bio/KBase/AppService/AppServiceImpl.pm`, backed by `SchedulerDB.pm`.

- **Editing the API:** change `AppService.spec`, run `make compile-typespec`
  (regenerates `Service.pm` and the Perl/Python/JS clients, and injects an empty
  `#BEGIN/#END <method>` stub into `AppServiceImpl.pm`), then fill the stub. The
  Perl/Python clients are generated (untracked here); only `Client.js` is tracked.
- **Auth in Impl methods:** `$ctx = $Bio::KBase::AppService::Service::CallContext`
  gives `$ctx->user_id` and `$ctx->token`. **Admin check is role-based:**
  `P3AuthToken->new(token=>$ctx->token)->is_admin` (token has `|scope=user|` +
  `|roles=admin|`). (`Util.pm` also hardcodes `olson@patricbrc.org` for a
  service-down bypass — unrelated to query auth.)
- **`enumerate_tasks_qstat`** (added 2026-07, PR
  https://github.com/BV-BRC/app_service/pull/37, branch `feature/qstat-in-api`):
  remote `p3x-qstat`-style queue listing with **server-enforced visibility**.
  Non-admins see only their own jobs (owner clause forced in SQL by
  `_build_qstat_conditions`); `all_users` returns the whole queue but foreign
  rows are **masked** in the Impl (id/owner/app blanked, params dropped). Admins
  see all, unmasked. Returns cluster-execution fields (join Task⟕TaskExecution⟕
  ClusterJob) and UTC ISO-8601 times. Client: `p3_cli/scripts/p3-qstat.pl`
  (converts to local time by default, `--utc` to override). Not live until the
  service is redeployed.
- **`p3x-set-site-container.pl`** (PR
  https://github.com/BV-BRC/app_service/pull/38): first arg matches a `site_type`
  (tried first) **or** a domain against the host of `base_url` with subdomain
  semantics (`maage-brc.org` hits `www.`+`dev.`; `dev.maage-brc.org` hits one).
- **App-spec resolution at submit (preflight-dependent):** the spec a job
  validates params against is **frozen into `Task.app_spec` at submit** and
  replayed at runtime (never re-read from the container the job runs in). Its
  *source branches on preflight* (`p3x-submit-job.pl:104-134`): if preflight runs
  (normal submission, or a non-staff user), the spec is read **fresh from the
  container** via `run_preflight()`; if a **staff** user disables preflight
  (`p3-submit-* --preflight cpu=… memory=… runtime=…` → `disable_preflight`), the
  spec is pulled from the **DB `Application.spec` cache** (`SELECT spec FROM
  Application`). `create_task` stores whichever was chosen (`SchedulerDB.pm:197`).
  `AppScript::preprocess_parameters` (`AppScript.pm:728`) then **silently drops**
  any submitted param not declared in that spec (warns "provided … but not
  specified in the app spec"; kept only in `raw_params`, never reaches the Impl).
  **Gotcha:** the DB cache is refreshed only by **`p3x-load-app-specs`** (→
  `Scheduler::load_apps` `update_or_new`, `Scheduler.pm:374`), so it drifts stale
  vs. the container until reloaded — a staff `--preflight` submission then validates

### p3_core — RQL `terms()` vs `in()` for ID lists

**The rule is `terms()` for a large value list (hundreds+), `in()` for a handful
— but as of 2026-09-03 production still answers `terms()` with a 400, so
`P3DataAPI` sends `in()` and gates the switch behind `P3_RQL_TERMS`** (see
`P3DataAPI::id_list_op`, whose POD carries the measurements). Read the rest of
this section as the design and the evidence for that gate, not as current
behavior.

Both operators take the same shape — `terms(genome_id,(123.456,789.012))` — but
they compile to very different Solr queries:

| | emitted | Solr side |
|---|---|---|
| `in(f,(a,b,c))` | `&q=` … `f:(a OR b OR c)` | boolean query, **one clause per value**, scored |
| `terms(f,(a,b,c))` | `&fq={!terms f=f}a,b,c` | hash-set match, filter-cached, **unscored** |

`lib/solrjs/rql.js:474` collects the clause and `:108` emits it. Two independent
wins: the `{!terms}` parser uses a hash set instead of building a clause per
value (on a few thousand values the clause tree is the dominant cost of the
query, and it can hit `maxBooleanClauses`), and it lands in `&fq=` so it goes
through the filter cache.

The tradeoff is the flip side of that second point: an `fq` does not contribute
to relevance scoring, so do **not** swap `in()` for `terms()` inside a clause
whose ranking you depend on. For ID-list lookups — which is what all of these
are — that is irrelevant.

- **Two `in()` forms that `terms()` silently breaks**, both present in
  `P3DataAPI.pm` and both left as `in()` on purpose (with comments saying so):
  the **subquery** form `in(feature_id,FeatureGroup(/path))` /
  `in(genome_id,GenomeGroup(/path))`, where the argument is a reference the API
  resolves server-side rather than a value list; and **wildcards**,
  `in(feature_type,(*rna,*RNA))` — `{!terms}` is literal-match only, so it would
  hunt for a feature type spelled `*rna` and return nothing. Neither fails
  loudly; both just return no rows.
- Six sites in `P3DataAPI.pm` now call **`id_list_op()`** instead of naming an
  operator (2026-09-03): `lookup_sequence_data` (md5 batch), the two `$id_field`
  feature-id lookups, and the three `genome_id` list queries.
- **One deployment defect still forces the `in()` default: production does not
  implement the operator.** `www.bv-brc.org/api` and
  `p3.theseed.org/services/data_api` both answer **400**; only
  `alpha.bv-brc.org/api` answers 200. The error is not "unknown operator" but a
  Solr exception (`A Database Error Occured` /
  `org.apache.solr.common.SolrException`; an earlier build phrased it
  `{"msg":"undefined field object","code":400}`) — the older `rql.js` mangles
  the clause rather than rejecting it. `www.bv-brc.org/api` is `P3DataAPI`'s
  **default url**, so an unconditional swap breaks every caller.
  `t/client-tests/p3-rql-terms.t` is the probe — skips unless
  `P3_TERMS_TEST_URL` names an endpoint, checks all three conditions that must
  hold before flipping; `p3-rql-terms-bench.pl` next door is the timing
  counterpart.
- **Two further alpha defects existed and were fixed by an API update on
  2026-09-03.** Both are now regression targets rather than known-bad state —
  worth knowing because each hid from an obvious test.
  1. **Truncation on `genome_feature`.** `terms()` with a `limit` of **≥ 10,000**
     returned **HTTP 200 with a one-byte body (`[`)** whenever the match was
     exhausted before the limit: `limit(9999)` → 250 rows, `limit(10000)` →
     truncated. `chunk_size` is 25,000, so every paged `genome_feature` query hit
     it — but a *small* limit hid it completely, which is why it survived the
     first round of testing. The `feature_sequence` core was never affected.
  2. **A co-occurring clause made `terms()` much slower.** Moving the id list to
     `&fq=` left whatever else was in the query as the *scored* clause, so a
     low-selectivity companion became the dominant cost. Same 6,053 `patric_id`s:
     id list alone **0.86×** (a win), id list + `in(feature_type,(mat_peptide,CDS))`
     **1.65×** (a loss) — and that second shape is exactly what
     `retrieve_protein_feature_sequence` / `retrieve_nucleotide_feature_sequence`
     send, making the former **1.93× slower** end to end. Post-fix the companion
     clause is nearly free (0.35× / 0.41×) and that call runs **0.79×**. The
     general lesson survives the fix: benchmark the *query shape the code sends*,
     not the operator in isolation.
- **The operator is correct and now uniformly faster where deployed.** Against
  alpha, `in()` and `terms()` agree row for row at every size on both cores, and
  `terms()` wins throughout — 0.39–0.90× on `genome_feature`, 0.49–0.85× on
  `feature_sequence` (n = 100 … 15,000). Per call site: protein 3.12s → 2.56s,
  nucleotide 4.27s → 2.64s, md5 aa 1.54s → 1.15s, na 2.53s → 1.19s.
- **This is distinct from the other ID-list mechanism in the tree**, which is
  easy to confuse with it: `BatchJoiner` / `CrossCollectionSourceStream` also
  build `{!terms}` filters, but do it in JS via `fetchByIds` rather than through
  RQL. Same Solr-side construct, different entry point.
- **Why it matters operationally:** on 2026-09-03 twelve concurrent BLAST build
  workers calling `lookup_sequence_data` with **5,000 md5s per `in()`** (a
  165,203-byte request body) preceded the API tier wedging — three node workers
  CPU-pegged, `/api` returning zero bytes while the web front end still answered
  in 113 ms, and Cloudflare handing eleven genera a bare `error code: 524`
  inside a three-second window.

#### Retry against the data API — a 200 is not a usable answer

These are the "p3_core notes on retry policy" the `p3_auth` section points at.
The retry machinery itself (`P3ClientUA::retry_request`, `classify_response`,
`backoff_delay`) lives in **`p3_auth`** and is documented there; what follows is
how it behaves against *this* API specifically.

- **`detect_truncated_body` is inert against the data API, on every path.** It
  compares the body length against **`Content-Length`** and returns the response
  untouched when there is none (`return $res unless defined($want)`) — and the
  API serves **chunked**. Measured as LWP sees it, not just via curl's HTTP/2:
  `/api` and `/api-internal`, schema *and* query endpoints, all answer
  `Transfer-Encoding: chunked` with `content_length` undef. So the three call
  sites that wrap it (`P3DataAPI:419`, `:972`, `P3WorkspaceClient:2681`) get no
  protection from it here. The Workspace one targets **Shock**, a different
  server that may genuinely send `Content-Length` — unverified.
- **What actually protects the query paths is the decode retry**, not that
  helper: `submit_query` treats an undecodable body as transient and retries it
  (pinned by test 15 in `t/client-tests/p3-solr-retry.t`). Keep that in mind
  before "simplifying" it away as redundant with `detect_truncated_body`.
- **`classify_response` calls every 2xx `NO_RETRY`**, so any body-level failure
  is invisible to the retry layer unless the caller downgrades it. The idiom for
  doing so is to synthesize a **502 `HTTP::Response`** — what
  `detect_truncated_body` does — and return it from `retry_request`'s **`send`**
  hook. Do it there rather than adding an option to `P3ClientUA`: a cross-module
  signature change recreates the skew that left `p3_core` master calling an
  undefined `retry_request` for three weeks (see the p3_auth section).
- **A failure that parses is permanent; one that does not is transient.** The
  schema lookup got this wrong and it cost a GenomeAnnotation job (2026-10-05):
  a 200 with an empty/truncated/HTML body reached the uniqueKey check unretried,
  `decode_json` died inside a bare `eval` whose error was discarded, and the code
  reported **`core 'taxonomy' reports no uniqueKey in its schema`** — about a core
  whose schema has had `taxon_id` throughout. Four unrelated causes produced the
  byte-identical message at `attempts=1`. Fixed in
  [PR #27](https://github.com/BV-BRC/p3_core/pull/27). The split to preserve:
  retrying a genuinely keyless core would burn the whole **300 s** budget on an
  answer that cannot change, so only the unparseable case is made retryable.
- **Put the evidence in the message.** A transient is gone by the time anyone
  reads the stderr, so an error about a response body should carry content-type,
  byte count and a short snippet — otherwise Cloudflare HTML, a truncated read
  and a real schema change are indistinguishable in the only artifact that
  survives. Strip JSON::XS's `at <file> line <n>`: it names our own `decode_json`
  call and reads as if the bug were there.
- **When adding a test here, feed it a malformed body.** Every schema test
  predating the fix used a well-formed one, which is exactly how this shipped.

### p3_solr_pipeline (genome indexing)

`service-scripts/rast2solr.pl` builds the Solr load documents (`genome.json`,
`genome_feature.json`, …) from a genome object / GTO. The **current** Solr schema
lives in `/home/olson/BV-BRC/schema-update-2026-0512/BV-BRC-Solr/<core>/managed-schema`
(e.g. `genome/managed-schema`) — **not** the stale `/home/olson/P3/patric_solr/`
copy. The genome core has **no `dynamicField` and no schemaless/unknown-field
handling**, so any field not in `managed-schema` is rejected at index time.

- **Field pass-through:** rast2solr.pl copies **every key** from the input
  object's `genotype_annotation` sub-hash straight into the genome doc under its
  original name (`while (my($k,$v)=each %{$genomeObj->{genotype_annotation}}) {
  $genome->{$k}=$v }`, ~line 276). So viral-typing field names originate upstream
  in whatever populated `genotype_annotation`, not in the indexer.
- **`passage_details` mystery:** the schema field is `passage` (singular);
  `passage_details` is **not** in the schema and **no code in this tree emits
  it**. rast2solr.pl only ever sets `$genome->{passage}`. The GenomeAnnotation
  spec's `genotype_annotation` typedef (`genome_annotation/GenomeAnnotation.spec`)
  lists `subtype/h_type/n_type/clades/lineage/clade/subclade/other_typing` — no
  `passage_details`. A doc carrying `passage_details` got it via the pass-through
  above (an out-of-typedef key on `genotype_annotation`, likely legacy IRD/ViPR
  data). It will fail to index against the current schema — fix at the source
  (rename to `passage` or drop the key), or add the field to `managed-schema`.

### homology_service (BLAST databases)

The service searches a *generation*: a dated directory of BLAST v5 databases plus
a `db.sqlite` catalog mapping taxon ids onto them. **`REBUILDING.md` (module top
level, added 2026-08-26) is the process of record** — build invocations, the
sqlite catalog, verification, publishing. `ImplementationNotes.md` is the older
design doc. **`DIAMOND-NOTES.md`** (2026-09-11) evaluates DIAMOND as a second
engine for the protein path — `--taxonlist` is a real analogue of `-taxids`, but
DIAMOND covers only 2 of the 8 combinations in `%search_type_map` and no
nucleotide database at all, and the installed 2.0.9 lacks the `--no-parse-seqids`
(v2.1.7+) our `gnl|fig|...` accessions require. Consider before the next rebuild;
nothing is implemented. Live generation is named in **two** `deploy.cfg` stanzas,
`[homology_service]` *and* `[HomologyService]`, each setting
`blast-db-search-path` + `blast-sqlite-db`; updating one leaves half the service
on the old data.

A generation = `by-genus-bacterial/` (~11,970 DBs) + `by-genus-viral/` (~195,
keyed by **family** — the directory name is historical and wrong) + `ref/` (6
curated) + `db.sqlite`. Each name exists in three types (`features.faa`,
`features.fna`, `contigs.fna`), each with `.taxids`/`.taxlist`/`.glist` sidecars.
**~1.8 TB total**, essentially all bacterial (703 + 641 + 415 GB).

- **A rebuild must target a fresh empty dated directory.** `p3x-create-blast-db.pl:94-100`
  skips any database that already has a non-empty `.taxids` plus blast files, and
  `p3x-build-pathogen-blastdbs` has **no `--overwrite` passthrough** — so a rerun
  into a populated tree cannot rebuild anything. That is how `data.2022-0916`
  shipped 9 damaged databases: the 09-20 rerun was refused for 5,110 of them.
  Watch `grep -rl 'already exists, skipping' $NEW/logs/ | wc -l` staying 0.
- **Build on local disk, for contention not speed.** The I/O is large-block
  sequential, so SSD-vs-spinning is second order; the real argument is keeping
  1.8 TB of writes off the shared `/vol/blastdb` netapp (85% full, serving live
  queries). Cost is a ~1.8 TB copy at publish time.
- **Compile-time failure signature.** `p3x-create-blast-db` loads
  `PerlIO::via::Blockwise` (needs `IO::AIO`) and `BerkeleyDB`; the driver loads
  neither, so a missing module starts normally and kills every worker at BEGIN.
  It surfaces as `Failure running p3x-create-blast-db …: No such file or directory 512`
  — `$?` 512 = exit 2, because Perl's `die` exits with `$!` when nonzero and
  `Can't locate Foo.pm in @INC` is ENOENT; the driver then prints the *parent's*
  stale `$!`. **No per-genus log files at all** is the tell. Check with
  `perl -c scripts/p3x-create-blast-db.pl`.
- **The build now verifies itself** (commit `eb87cd8`, branch
  `feature/db-sqlite-build-scripts`): the two child fasta/taxid writes in
  `process_from_download_files` are checked (`IO::Handle::error` for the opaque
  `print_alignment_as_fasta`, `or die` for the taxid print), and
  `verify_record_count` compares `number-of-sequences` from the `.pjs`/`.njs`
  sidecar against the `.taxids` line count after makeblastdb, **unlinking
  `.taxids`** on mismatch so neither the skip guard nor the catalog loader accepts
  the database. Child-side checks alone are not enough: `LPTScheduler::run`
  discards the child exit status that `Proc::ParallelLoop` records in
  `@Exit_Status`, so the parent `cat`s partial files regardless.
- **The tolerance is 0, and 5% was empirically wrong.** Validated against the
  known-damaged production DBs, a 5% threshold caught **none** of them (Klebsiella
  1.57% short, Salmonella 4.96%, Staphylococcus 1,270 *extra*). Default is exact
  equality with `abs($delta)` so a surplus fails too; the viral path passes
  `--max-missing-fraction 0.03` because makeblastdb deterministically rejects a
  few records there (45 viral DBs short, all ≤2.4%).
  **Blind spot:** `Acinetobacter.features.faa` is damaged yet its counts match
  exactly — that one needs the taxid-coverage or chimera-length detector.
- **`--curated-directory` is a no-op: the loader never writes the flag.**
  (Corrects an earlier note here that blamed path matching.)
  **Status 2026-10-20: the fix below is written but only in the working tree,
  uncommitted** — `p3x-create-databases-lookup.pl` has an 18-line local diff
  adding the `UPDATE` at :123. The line numbers in this bullet are **HEAD's**
  (`7c50d4f`); in the dirty tree they are 112/113/122. Nothing is committed or

  `bacteria-archaea`, and why the `NOT g.curated` filter in
  `BlastDatabasesSQL::search_taxa:109` is inert. `BlastDatabasesSQL::databases()`
  (`SELECT name FROM GenomeGroup WHERE curated`) consequently returns nothing —
  it has zero callers, so nothing noticed. Fix is an explicit
  `UPDATE GenomeGroup SET curated = ? WHERE name = ?` after the insert (must be a
  separate statement: `INSERT OR IGNORE` is what makes the walk idempotent across
  a group's three databases, and the second and third rows would otherwise skip
  the flag). Whether the path matching *also* works is untested — it was never
  reached.
- **The `ref/` invocations are only half recorded.** `ImplementationNotes.md:64`
  has the viral one verbatim; the `bacteria-archaea` one is nowhere in the tree
  and is reconstructed (`--taxon 2 --taxon 2157 --reference --representative`,
  matching the shipped 6,352 genomes / 6,232 taxa). The six production build logs
  are `data.2022-0916/logs/log.{bacteria,virus}.{aa,dna}.{features,contigs}.out`.
- See also `scripts/db-schema.sql` + the three `p3x-create-taxonomy-*` /
  `p3x-create-databases-lookup` steps, whose order is load-bearing (the lineage
  builder reads `TaxonInDatabase`, created by the lookup loader).

#### The plasmid databases (built 2026-09-04; not yet in any catalog)

Three standalone BLAST databases of BV-BRC's plasmid contigs and the features on
them — `/blast-build/plasmid-2026-0904/`, 23 GB: 69,373 contigs / 7,609,103
proteins / 7,723,972 genes. Builder `scripts/p3x-create-plasmid-blast-db.pl`,
documented in **`PLASMID-DB.md`** (selection, cache traps, verification).
**`PLAN-plasmid-service-integration.md`** (written 2026-09-04, *planned, not
implemented*) is how they get into the service. Note it and `DIAMOND-NOTES.md`
are **untracked** — they exist only in this working tree, so a fresh clone has
neither (`PLASMID-DB.md` is committed; `REBUILDING.md` has uncommitted edits).

- **Separate script on purpose.** `p3x-create-blast-db.pl`'s front end is a
  genome-level Solr query with taxon/quality/reference filters; plasmid selection
  is **contig-level** (`sequence_type:plasmid AND public:true`, length
  `[1000, 2000000]`) and orthogonal to all of it. Patterns copied, file untouched.
- **`annotation=PATRIC` + `feature_type=CDS` is not optional** for any feature
  count drawn from `genome_feature`: `accession:CP093325` returns 35,246 features
  but only 12,226 PATRIC ones. Omitting it roughly **triples** the count with
  RefSeq duplicate calls of the same genes. Worth remembering whenever a
  BLAST-database sequence total is compared against a website figure.
- **`sequence_id` is the join key, not `accession`** — 90,705 plasmid rows carry
  only 83,819 distinct accessions (one appears 14 times), and an accession spans
  multiple genomes *and* both annotation sources.
- **Three obstacles before they can be catalogued**, all confirmed:
  1. **Two-part filenames.** The build emitted `plasmids.{fna,faa,ffn}`, but the
     loader parses `<tag>.<ftype>.<dbtype>.taxids` with
     `/^(.*)\.([^.]+)\.([^.]+)$/` — a two-part name leaves all three captures
     `undef` and the run dies on NOT NULL. The convention is three-part, and the
     **gene** database is spelled **`.features.fna`, not `.ffn`** (the loader
     remaps `features`+`fna` → dbtype `ffn`).
  2. **The `curated` bug above.** It matters more here than for `ref/`: an
     unflagged `plasmids` group covering 27,769 genomes' taxa is silently pulled
     into every ordinary `taxon_list` search by `search_taxa`, duplicating content
     the genus databases already hold.
  3. **Contig deflines don't parse.** `HomologySearch::decode_title` demands
     `\s{3}` before `[` and no padding inside; contigs are written
     `… complete sequence. [ Name | 2994555.3 ]` (one space, padded) and match
     nothing, so an fna hit carries no genome name or id. Pre-existing — it
     affects every genus contig hit in production too. The safe fix is a **third**
     alternative requiring a literal `| <genome-id>` inside the brackets, which is
     what keeps it from misfiring on a product name ending in `[Escherichia coli]`.
- **A second database directory is not possible.** `Config.pm.tt` interpolates a
  single scalar into a one-element list
  (`blast_db_search_path => ['[% blast_db_search_path %]']`), so the plasmid tree
  must be moved *inside* the generation — and as a **real directory, not a
  symlink**, because `p3x-create-databases-lookup` uses `File::Find` without
  `follow`. (`Config.pm` is generated by `make build-libs`; never hand-edit it.)
- **Two independent "precomputed database" surfaces**, easy to confuse. The
  JSONRPC one (`Util.pm:680` `enumerate_databases`, a directory glob) is **dead** —
  its `blast-db-databases` key is commented out in both `deploy.cfg` stanzas. The
  live one is the app path `db_source=precomputed_database` +
  `db_precomputed_database=<name>` → `BlastDatabasesSQL::find_precomputed_database`
  (which, note, does **not** filter on `curated`). Two names use it today:
  `bacteria-archaea`, `viral-reference`.
- **There is no discovery surface.** `databases()` has zero callers and the
  JSONRPC path is unconfigured; the two live names reach users only because the
  web UI hardcodes them. A third name is API-reachable only until the UI adds it.

#### Sketch identity — the silent-drop trap

`mash` records **the path of the fasta it sketched** as the sketch's id. It
survives `mash paste` and is column 0 of `mash dist`, and `minhash-search.pl`
used to recover the genome id from it with `m,genomes/((\d+)\.(\d+)),`. A sketch
built anywhere without a literal `genomes/` component therefore yielded `undef`
and **the hit was dropped with no diagnostic**. That is why the viral builder
sketches out of a scratch directory deliberately named `/dev/shm/tmp.$$.genomes/`.

- `minhash-build-sketches.pl` now stamps the id with **`mash sketch -I <gid>`**,
  so a sketch is self-describing wherever its fasta lived. `minhash-search.pl`
  resolves bare id → legacy path form → anchored basename, and **warns** on an
  id it cannot parse instead of dropping it.
- **Deployment order is load-bearing:** ship the updated `minhash-search` before
  publishing sketches built by the current builder. The 2026-09 `all.msh` is
  **34% bare-id** (355,926 of 1,035,624 — the rest are pre-existing sketches the
  builder correctly left alone), and an old search loses every one of them
  silently.

#### The bacterial builder is API-driven

It used to `readdir` the downloads tree, so a genome with no download file was
never seen and could not be sketched — or reported. Coverage there is very
uneven (sampled 2026-09: 182/200 missing in one genome-id band, 0/200 in others,
and all 300 most-recently-loaded genomes absent). It now enumerates from the data
API, probes the tree per genome, and batch-fetches the misses — the same shape as
`homology_service/scripts/p3x-create-blast-db.pl`, whose
`prefetch_missing_genomes()` the fetch code is adapted from. Note
`P3DataAPI::retrieve_contigs_in_genomes` (what the viral builder uses) issues one
query **per genome**, so passing it a list batches nothing.

- Options worth knowing: `--fetch-dir` (persistent contig cache, written
  temp-then-rename; a genome returning no contigs leaves no file so it is retried
  next run), `--genomes-from` (feed a `--missing-list` back in; the restriction is
  pushed into the query rather than filtering a million rows), `--limit` +
  `--dry-run` for smoke tests, `--stale-list`, `--missing-list`.
- **The genome set is defined twice and must agree.** The builder spells it as
  raw Solr `fq` params and `minhash-create-combined-sketches.pl` spells it in RQL,
  because they use different P3DataAPI entry points: public Bacteria+Archaea,
  `genome_quality:Good`, `genome_length:*`, and `ne(genome_status,Deprecated)`
  (= `fq => -genome_status:Deprecated`). **1,035,704** as of 2026-09; the two
  spellings were verified to return identical sets, zero symmetric difference.
  Before they were aligned the combiner enumerated every public genome and
  reported a permanent ~330k shortfall no amount of building could close.
  There is deliberately **no shared module** holding the filter list: the
  Makefile's `deploy-client` target deploys scripts without libs.
- 2026-09 result: 1,035,624 sketched. The 80-genome shortfall is genomes with
  **zero `genome_sequence` rows in the API** — there is nothing to sketch, and
  the builder's `missing-list` and the combiner's `--missing-data` agree exactly.

#### `mash paste` and `vm.max_map_count`

`mash paste` mmaps **one region per input sketch**, so it fails outright past
`vm.max_map_count` (1,048,576 on lime):

```
Error: could not memory-map file .../11320.230343.msh of size 8488
```

The message misleads twice: the limit is a **count of mappings, not a size**, and
the file it names is small and blameless — just the one that ran the process out
of them. Measured: 1,000,000 inputs paste fine, 1,100,000 fail.

- Raising the sysctl (the old advice, still in that script's header comment) no
  longer scales. Both combined scripts now chunk via **`paste_files()`**, default
  half of `/proc/sys/vm/max_map_count`, override with `MINHASH_PASTE_CHUNK`. A
  two-stage paste is exactly equivalent — verified row for row including ids.
- **Read family counts post-filter.** The viral script drops private and
  `genome_status=Partial` genomes, which takes Retroviridae from 1,240,397 raw to
  99,298. Only Orthomyxoviridae (1,223,270 post-filter) actually exceeded the
  limit. The bacterial `all` paste is unfiltered and cleared it by just 12,952.

#### The flat sketch directory is fine — don't shard it

`sketches/` holds ~1M files in **one** directory and that is not worth changing.
Benchmarked on ext4 with `dir_index` (2026-09, 1M × 8 KB files, warm cache),
flat vs 1-level (1024 dirs) vs 2-level (4096 dirs):

| operation | flat | 1-level | 2-level |
|---|---|---|---|
| create 1M, single-threaded | 40.8 s | 40.8 s | 39.6 s |
| random `stat` | 395k/s | 380k/s | 360k/s |
| random `open`+read | 83.2k/s | 79.3k/s | 77.9k/s |
| recursive `readdir` | 0.313 s | 0.325 s | 0.379 s |

Flat wins or ties everywhere — htree lookup in a 1M-entry directory is
effectively free, and sharding only adds path components to resolve. The
folklore about hashed subdirectories is from ext2/ext3-without-htree and UFS,
where lookup was a linear scan.

**The one exception, and why it still doesn't matter here:** ext4 takes the
directory inode lock on create, so *parallel* creation does benefit — hugely.
At 32 workers, flat manages 42,266 files/s (worse than its own 47,102 at 8
workers, i.e. lock-saturated) against 225,070 for 2-level, a **5.3×** win. But
sketching one genome costs ~0.10 s of mash CPU, so for ~200k genomes that 5.3×
saves about **four seconds** against a job measured in hours. Sharding would
mean changing `lib/Bio/P3/Minhash/MinhashImpl.pm:375` (master's numbering), both combine scripts and the builder, plus
relocating ~890k files — real risk to the live service for nothing. If the
build ever feels slow, `--parallel` and `--fetch-batch-size` are the levers, not
the layout.

#### Viral combine quirks

- **20 of 354 families are entirely `Partial`**, so they legitimately paste to
  nothing and produce no file. That is a skip, not a failure — a completeness
  check that cannot tell the difference will refuse to build the buckets.
- `--parallel 1` packs every family into **one** LPTScheduler bin, so a single
  `die` used to lose all 354 (Orthomyxoviridae sorts first, being largest).
  Failures are now isolated and listed before the bucketing stage, which
  otherwise surfaces them as an opaque mash error naming an innocent family.
- `--skip-existing` reuses family sketches already in the output directory, so a
  run that fails late can be resumed without repeating the expensive pastes.
- A family literally named **`null`** (38 genomes) is real upstream data: the API
  returns the *string* `'null'` as `family` for those records.
- 14.9 GB of family sketches fits the script's 20 GB bucket ceiling, so the
  result is a single `all-viral-01.msh` — `deploy.cfg`'s references to
  `all-viral-02/03.msh` name files that do not exist in this build or the 2024 one.

#### Version stamping and the User-Agent (2026-08)

The top-level **`version`** package holds the build version and the product
identity, and derives from them the User-Agent every SDK HTTP client sends. It
replaced the fixed `BV-BRC P3 Client`, and is now set on the data API (`api`),
Workspace and AppService JSONRPC, Shock downloads, `auth` login, and NCBI
eutils (`sra`) — the JSONRPC/Shock/login calls previously sent Go's default
`Go-http-client/1.1`.

- **Three identities, and the UA names the product, not the library**
  (revised 2026-08-18): **`bvbrc-cli-go/<version>`** from the `p3-*` tools,
  **`bvbrc-auth-go/<version>`** from `p3-login`, and `bvbrc-go-sdk/<version>`
  only from a program that links these packages as a library. Mirrors the Perl
  `bvbrc-cli-perl` / `bvbrc-auth-perl`. `P3_USER_AGENT` (whole string),
  `WithUserAgent` and `--user-agent` still override, in that order over the
  product.
- **The product is declared in the source, not stamped by the build** — the
  opposite of the version, because unlike the version it *is* knowable from the
  source, and a `go install …/cmd/p3-ls@v2` build should still identify itself.
  134 commands blank-import **`internal/cliproduct`** (its `init` calls
  `version.SetProduct`) — including all 37 `rast-*`, which therefore also
  identify as `bvbrc-cli-go`; `cmd/p3-login/main.go` calls
  `version.SetProduct(version.AuthProduct)` itself. `p3-echo`, `p3-fasta-md5`
  and `p3-merge` make no requests and declare nothing.
  **`TestEveryCommandDeclaresAProduct`** (in `internal/cliproduct`) parses every
  `cmd/*/main.go` and fails if a new command forgets — without it a forgotten
  import silently reverts that tool to `bvbrc-go-sdk`.
- **Perl's `P3_CLIENT_PRODUCT` is deliberately not read on the Go side.** A Perl
  `p3-*` wrapper exports it, so honoring it would make a Go tool invoked from
  one announce itself as `bvbrc-cli-perl`. Go has a compile-time seam and does
  not need the environment one.
- **Don't cache `version.UserAgent()` in a package-level var:** an imported
  package initializes *before* the `main` package's `init`, so it would miss the
  product. `api.DefaultUserAgent` is exactly this and is therefore the library
  name only — `NewClient` resolves the real UA per request.
- Verified live 2026-08-18: `bvbrc-cli-go` and `bvbrc-auth-go` (with and without
  a version suffix) all get **200** from `www.patricbrc.org/api` while
  `libwww-perl` gets 403, and a plain **401** from
  `user.patricbrc.org/authenticate` — neither new name is on the 1010 list.
- **Where the version comes from:** `scripts/version.sh` — `$VERSION` if set
  (the release workflow sets it from the pushed tag), else the tag when HEAD is
  exactly tagged (leading `v` stripped), else the short commit hash
  (`+"-dirty"`), else `unknown`. `Makefile` and all four `build-*.sh` scripts
  stamp it with
  `-ldflags "-X github.com/BV-BRC/BV-BRC-Go-SDK/version.Version=$VERSION"`; the
  build scripts also default `VERSION` from it instead of the old literal
  `1.0.0`, so a local (non-CI) release build names its artifacts after the tag
  or hash.
- **Gotcha:** a bare `go build -buildvcs=false ./...` stamps nothing, and
  `-buildvcs=false` also denies the `debug.ReadBuildInfo` fallback its VCS data,
  so such a binary reports `bvbrc-cli-go/unknown` — right product, no version.
  Use `make` (or a build script) for anything whose UA matters.
- **The module path ends in `/v2`, and that is load-bearing** (renamed
  2026-10-20, PR https://github.com/BV-BRC/BV-BRC-Go-SDK/pull/17). Every
  import is `github.com/BV-BRC/BV-BRC-Go-SDK/v2/<package>`. Before the rename
  `go.mod` declared the path *without* a major-version suffix while every tag
  was v2.x, so the proxy rejected all of them and **a plain `go get` silently
  resolved to a pseudo-version of `main`** rather than the release — worse
  than an error, since the caller believes they pinned it. Retagging could
  never have fixed that: the only versions an unsuffixed path accepts are v0
  and v1, and the `+incompatible` escape hatch exists only for repos with no
  `go.mod`.
  - **v2.0.17 is the first release that can be named from Go**, verified:
    `go get github.com/BV-BRC/BV-BRC-Go-SDK/v2@v2.0.17` resolves, and so does
    `go install …/v2/cmd/p3-ls@v2.0.17`. **Do not check this with the proxy's
    `@v/list`** — it happily echoes v2.0.0–v2.0.16 under the `/v2` path even
    though none of them resolve. Only a per-version fetch tells the truth:
    `…/v2/@v/v2.0.17.info` → 200, `…/v2/@v/v2.0.16.info` → 404
    `go.mod has non-.../v2 module path`. **Tags v2.0.1–v2.0.16 are permanently
    unusable** — the proxy objects to the `go.mod` recorded *inside* each tag,
    so nothing but re-tagging would change it, and that republishes conda
    packages over themselves. Leave them.
  - **A release tag must be cut from a commit whose `go.mod` already says
    `/v2`**, or the tag is dead on arrival exactly as the old ones are.
  - **Five files name the version package by its full import path** — the
    `Makefile`'s `VERSION_PKG` and four `build-*.sh` `LDFLAGS_VERSION` — and
    **the linker silently ignores an `-X` whose path does not resolve**. Miss
    one in a future rename and that platform's binaries build fine, archive at
    the right size, and report `unknown` from both `--version` and the UA.
    `TestVersionStampPathTracksTheModulePath` (`packaging_test.go`) derives the
    expected path from `go.mod` and guards all five.
  - A `go install` build takes the `debug.ReadBuildInfo` path, where
    `Main.Version` carries a leading `v`; `version.normalizeModuleVersion`
    strips it so the same release does not report `2.0.17` from the archive and
    `v2.0.17` from `go install` — i.e. two different User-Agents for identical
    code.
- **Check a shipped binary** without running it: `go version -m <binary> | grep
  ldflags` prints the `-X …/version.Version=<v>` it was built with. Confirmed on
  the v2.0.13 release tarball (`-s -w -X …version.Version=2.0.13`) — v2.0.13 is
  the first release whose artifacts carry the tag version instead of the old
  hardcoded `1.0.0`.
- **`--version` and `--debug-http`, on all commands** — 101 when the PR
  landed, all 138 now that the `rast-*` family uses the same root (PR
  https://github.com/BV-BRC/BV-BRC-Go-SDK/pull/8, branch
  `feature/version-flag`). `--version` prints `p3-ls 2.0.14` then
  `bvbrc-cli-go/2.0.14 linux/amd64 go1.25.6` — the second line is the **exact
  UA that binary sends**, so it shows the product and any `P3_USER_AGENT`
  override, which is the line to quote in a 1010 report. An unstamped build
  says `unknown` in both. `p3_cli` has no `--version` equivalent.
  - `main` calls **`cliroot.Execute(rootCmd)`**, not `rootCmd.Execute()`.
    `internal/cliroot` is a **leaf** package (cobra + `version` + `httpdiag`,
    all stdlib-only) on purpose: `internal/cli` pulls in `api` and `sra`, which
    would make `p3-echo`/`p3-fasta-md5`/`p3-merge` link the API client just to
    print a version. **`TestEveryCommandUsesTheSharedRoot`** enforces the call,
    mirroring `TestEveryCommandDeclaresAProduct` — skipping it still builds and
    still works, it just silently has neither flag.
  - **`--debug-http` is the flag form of `P3_DEBUG_HTTP`**, which stays the
    documented switch. Before this only the **40** commands carrying
    `DataOptions` had one (`--debug`), plus `p3-login`'s bespoke copy (now
    removed in favour of the shared flag): every `p3-submit-*`, `p3-ls`,
    `p3-cp`, `p3-job-status` — i.e. the Workspace and AppService paths — had no
    flag at all for the case the diagnostics exist to serve. It is a
    `pflag.Value` that calls `httpdiag.SetEnabled(true)` from `Set`, during
    parsing; reading a bool later would mean `PersistentPreRun` (commands define
    their own) or `cobra.OnInitialize` (global state that accumulates).
  - **Why `--version` is declared by hand:** cobra's `InitDefaultVersionFlag`
    claims **`-v`** whenever that shorthand is free, and 8 commands already bind
    it (5 `--verbose`, 3 `--reverse`) — the default would make `-v` mean
    "version" in 93 tools and something else in 8. cobra still does the
    printing; it only looks up a bool flag named `version`.
  - The UA reaches the output via the command's **`Annotations`**, not the
    template source, so a `{{…}}` in `P3_USER_AGENT` prints verbatim instead of
    being executed by `text/template`.

#### conda publishing (anaconda.org/bv-brc)

The `conda-publish` job builds four `noarch`-less platform packages
(linux-64 / linux-aarch64 / osx-64 / osx-arm64) from the **release tarballs**,
not from source, and uploads them as `bvbrc-cli`.

- **Nothing in the conda path was ever bound to a repo.** `meta.yaml` takes the
  download repo from `environ.get("GITHUB_REPOSITORY", "BV-BRC/BV-BRC-Go-SDK")`,
  `scripts/update-conda-recipe.sh` uses the same fallback for its checksum
  fetch, and the workflow passes `${{ github.repository }}`. The one literal
  `olsonanl` was `extra: recipe-maintainers:` (cosmetic, read by nothing) —
  updated to `BV-BRC` in PR BV-BRC#6.
- **The destination is org-owned:** `api.anaconda.org/package/bv-brc/bvbrc-cli`
  reports owner `BV-BRC` (`user_type: org`), file owner `bv-brc`. Both repos
  publish to the same channel, so the binding that actually matters is the
  **token identity**, not the repo — it must belong to an account with upload
  rights to the `bv-brc` org. That is the one part of the BV-BRC setup that
  cannot be checked without a run.
- **`ANACONDA_API_TOKEN`** needs both `api:write` **and** `api:read`; a
  write-only token fails the upload late, after everything else has succeeded.
  `conda-publish` is last and `needs: release`, so such a failure leaves the
  GitHub release, archives and `.sif`s intact — fix the secret and

  second run silently overwrites the first's package. This is why the fork's
  workflow is disabled, and why a botched release is fixed by burning the
  number, not by deleting and re-pushing the tag.
- The committed `sha256` values in `meta.yaml` are stale placeholders by design;
  `update-conda-recipe.sh` patches them in CI from the release just published.

#### Archive layout

Each tarball/zip expands into a versioned directory
(`bvbrc-cli-<ver>-<platform>/`) containing `bin/` (the `p3-*` tools; `*.exe` at
the top on Windows), a generated `README.md`/`README.txt`, and `LICENSE` — not a
bare `bin/`. The README is produced by `scripts/make-readme.sh <version>
<platform>` (shared by all three build scripts; Unix vs Windows install notes by
platform). `LICENSE` (MIT) lives at the repo root, is bundled into every archive,
and is what conda's `license_file` resolves to. The conda recipe and
`build-apptainer.sh` account for this: conda-build flattens the single top-level
dir (so `build.sh` finds `bin/`), and the Apptainer def extracts with
`--strip-components=1` into `/usr/local`.

**Three installers ship alongside the archives and are easy to miss** — they
predate 2.0.16 but went undocumented in the README until 2026-10-20
(BV-BRC/BV-BRC-Go-SDK#16):

| asset | built by | installs to |
|---|---|---|
| `bvbrc-cli-<ver>-intel.pkg` | `build-macos-pkg.sh`, macOS runner (`pkgbuild`/`productbuild` need macOS) | `/usr/local/bin` |
| `bvbrc-cli-<ver>-apple-silicon.pkg` | same | `/usr/local/bin` |
| `bvbrc-cli-<ver>-windows-amd64-setup.exe` | NSIS, Windows runner | `C:\Program Files\BVBRC`, **appends to the system `PATH`**, writes an uninstaller + Add/Remove Programs entry |

**None is signed** — the release workflow names the macOS job "unsigned .pkg"
outright — so Finder blocks the `.pkg` (use `sudo installer -pkg … -target /`)
and SmartScreen warns on the setup.exe. **There is no ARM64 Windows
installer**; Windows-on-ARM must use the zip. There is **no Windows conda
package** either.

**Do not tell anyone to copy the tools into `C:\Windows\System32`** — the
README said so until 2026-10-20. It puts 138 executables in a system directory
where they cannot be upgraded or removed as a unit and can shadow system
commands.

#### The `rast-*` family (genome_annotation port, 2026-08)

**37 `rast-*` Go commands** ported from `genome_annotation/scripts/rast-*.pl`,
shipped first in **v2.0.15**. They are thin front-ends onto the GenomeAnnotation
JSONRPC service: read a genome typed object (GTO) as JSON on stdin, call one
method, write the GTO as pretty JSON on stdout. PRs
[#9](https://github.com/BV-BRC/BV-BRC-Go-SDK/pull/9) (packages),
[#10](https://github.com/BV-BRC/BV-BRC-Go-SDK/pull/10) (36 commands),
[#11](https://github.com/BV-BRC/BV-BRC-Go-SDK/pull/11) (`rast-export-SEED`),
[#12](https://github.com/BV-BRC/BV-BRC-Go-SDK/pull/12) (integration — see the
stacked-PR gotcha below). Design: `PLAN`-era notes in the plan file; live ledger
in `PORT_STATUS.md`.

- **The names collide with the Perl wrappers on purpose.** The Go tools are
  drop-in replacements for the 39 `rast-*` wrappers in `dev_container/bin/`;
  PATH order decides which runs. Same situation `p3-*` already has with
  `p3_cli`, now in two families.
- **Scope is 37 of 39.** Out: `rast-process-genome-batch` and
  `rast-download-genome-batch`, which need Shock/HandleService **upload** (the
  Go `workspace` package has download only) — and whose Perl originals do not
  compile in this tree anyway (`Bio::KBase::HandleService` is absent).
- **`genomeannotation/`** (repo root, peer of `appservice`): JSONRPC 1.1 client,
  `DefaultURL = https://p3.theseed.org/services/genome_annotation`, method
  prefix `GenomeAnnotation.`, 30-min default timeout overridable by
  **`CDMI_TIMEOUT`** (seconds, mirroring Perl). **Auth is optional** — several
  methods (`default_workflow`, `enumerate_special_protein_databases`) answer
  unauthenticated, so the `Authorization` header goes out only when a token
  exists and a missing token is never an error.
- **GTOs are never decoded.** Every pass-through method takes and returns
  `json.RawMessage`. Decoding through `map[string]interface{}` would renumber
  integers as floats and reorder keys. Pretty-print is
  `json.Indent(…, "", "   ")` — 3 spaces, matching `JSON::XS->new->pretty`.
  Key order still differs from Perl, so **parity is semantic (`jq -S .`), not
  byte-for-byte** — except `rast-export-SEED`, which is byte-identical
  (`diff -r`).
- **`internal/rastcli`** is the `CmdHelper.pm` equivalent (`-i/-o/--url`, the
  five `get_params_for_*` groups, the 14 export formats). The load-bearing
  detail is Perl's `if defined`: a param enters the map **only if the user set
  the flag** → Go `cmd.Flags().Changed(name)`. An unset flag must be absent, not
  zero.
- **`internal/seeddir`** is the port of `GenomeTypeObject::write_seed_dir`, the
  one piece with real algorithmic content and the only one that can be wrong
  silently. `map_CDS_to_peg` is hardcoded by the script: type `CDS` becomes
  `peg` everywhere, **including inside the feature id** (`.CDS.` → `.peg.`).
  - **`seeddir.Scalar` — the raw-JSON principle applied to scalars.** An
    annotation timestamp arrives as `1787100528.18559`; decoded to `float64`,
    Go prints `1.78710052818559e+09` and the file diverges. Keep the raw token.
- **Genetic-code divergence, deliberate.** `SeedUtils::genetic_code` spells its
  table-2/3 overrides in **RNA** (`AUA`, `UGA`, `CUU`) against a **DNA**-keyed
  table, so in Perl codes 2 and 3 silently translate as code 1. Go uses the real
  NCBI tables and **errors on an unsupported code** rather than mistranslating.
  Codes 1/4/11 (everything in this tree) are identical either way.
- **Three other on-purpose divergences from Perl:** `rast-process-genome`
  rejects the `--batch-input-*` flags (declared but never read in Perl) while
  `--timeout` actually works; `rast-query-classifier-groups` and `rast-classify`
  sort their output.
- **Packaging is prefix-glob-driven and was `p3-*`-only.** Widened in PR #9:
  `COMMANDS=$(ls -d cmd/*/ …)` in all four `build-*.sh`, rpm `%files` lists both
  `/usr/local/bin/p3-*` and `/usr/local/bin/rast-*`, `PREFIXES=(p3 rast)` in
  `conda-recipe/build.sh`, and `scripts/make-readme.sh` counts dynamically.
  **`packaging_test.go`** (hermetic, reads the scripts as text) derives the
  prefix set from `cmd/` and fails if any of those sites misses a family — the
  next family fails loudly instead of shipping half a toolkit.
- **README install-glob bug found by this work:** the shipped install
  instructions said `sudo cp .../bin/p3-* /usr/local/bin/`, which would have
  installed 101 of 138. All four Unix occurrences are now `bin/*`, Windows is
  `Copy-Item …\*.exe`, and the macOS quarantine command names both families.

#### Relationship to p3_cli (porting)

The Go SDK is a **curated subset** of `p3_cli` (not a full mirror): ~33 of the
137 Perl scripts are ported, one Go program per `cmd/<name>/main.go`. The build
enumerates commands dynamically (`Makefile` uses `$(wildcard cmd/*)`;
`build-*.sh` use `ls -d cmd/*/`), so a new `cmd/` directory is picked up
automatically — no registration needed. (The `rast-*` family mirrors
`genome_annotation/scripts/` instead and is complete at 37 of 39; see its
section above.)

`BV-BRC-Go-SDK/GO_PORT_PLAN.md` documents the original port design.
`BV-BRC-Go-SDK/PORT_STATUS.md` is the live ledger: per-command "synced to"
p3_cli commit + a stale-check command. Update a command's row when you port it.

**To find what needs (re)porting:** consult `PORT_STATUS.md`, or compare commit dates. Any `p3_cli` change
newer than the Go SDK's last relevant commit, touching a script that has a
`cmd/` counterpart, needs porting. New `p3_cli` submit scripts since the sync
are candidates for new Go commands.

**Submit-command port pattern** (Perl `CommonSpec`/`UploadSpec` → Go):
- Use `cmd/p3-submit-fastqutils/main.go` as the canonical template.
- Cobra `rootCmd`, `cobra.ExactArgs(2)` for `output-path output-name`.
- Four common flags: `-p/--workspace-path-prefix`, `-P/--workspace-upload-path`,
  `-f/--overwrite`, `--dry-run`.
- Perl `$uploader->normalize($x)` → trim leading `ws:` then `expandWorkspacePath`.
- Perl `$uploader->output_spec(@ARGV)` → the two positional args.
- Perl `fix_file_name`/local-or-ws file upload → `processFilename(ws, val, type, token)`.
- Perl `$commoner->submit($svc,$up,$params, App => 'desc')` → `app.StartApp2("App", params, startParams)`.
- Expose **only** the options the Perl `GetOptions` exposes (not every app-spec
  parameter). The authoritative parameter names/types/defaults are in the app's
  `app_specs/<App>.json` (in the service module, e.g. `bvbrc_docking/app_specs/`);
  the Perl script is the source of truth for the option→param mapping.

Build the Go binaries with `-buildvcs=false` (the git+svn mix in this tree breaks
VCS stamping): `go build -buildvcs=false -o bin/<cmd> ./cmd/<cmd>`.

#### Go/Perl parity (2026-06 alignment)

Go submit commands now match Perl behaviour in these areas:
- **Output-path validation** — `ws.RequireFolder` in all 25 submit cmds (mirrors Perl `UploadSpec`).
- **Genome-ID validation** — `api.RequireGenomeIDs` in the 5 genome-bearing cmds (mirrors Perl `GenomeIdSpec`).
- **Paired-end lib syntax** — all 11 paired-end commands accept both spellings
  identically (verified 2026-08 by diffing `--dry-run` params across forms).
  `NormalizePairedEndLibArgs` (`internal/cli/args.go`) pre-processes `os.Args`
  so `--paired-end-lib f1 f2` (two args, Perl `=s{2}` style) works alongside
  `--paired-end-lib f1,f2` / `--paired-end-lib=f1,f2`; it also rewrites the Perl
  plural alias `--paired-end-libs` to the singular (cobra has no flag aliases,
  and doing it here keeps it out of all 11 flag sets) and stops at a bare `--`.
  `cli.SplitPairedEndLib` then splits the one value — every command calls it
  instead of its own `strings.Split`, so the tolerated whitespace and the error
  text are the same everywhere; `cli.PairedEndLibUsage` likewise unifies the
  `--help` line. **Asymmetry that remains:** Perl accepts only the two-arg form
  (`ReadSpec.pm:255`), never the comma; and `p3-submit-genome-assembly.pl:117`
  declares its own `paired-end-lib=s{2}` without ReadSpec's `|paired-end-libs`
  alias, so that one Perl tool rejects the plural. Go is a superset of both.
- **Configurable User-Agent** — every SDK HTTP client sends one (see "Version stamping" below); overridable via `P3_USER_AGENT` or `WithUserAgent`/`--user-agent`. Required because `patricbrc.org` blocks `libwww-perl` via Cloudflare (error 1010). Both sides now name the product: Go sends `bvbrc-cli-go`/`bvbrc-auth-go`, Perl `bvbrc-cli-perl`/`bvbrc-auth-perl`.
- **Enum alignment** — Snippy in variation mapper/caller; `MASTADENOA` (not `MASTADENO_A`) in SubspeciesClassification; `progressiveMauve` in MSA.

#### Read-library parameter dialects (`internal/readspec`, 2026-08)

Apps **disagree** on the shape of their read-library params, and a wrong
parameter *name* fails silently: `AppScript::preprocess_parameters` drops
undeclared params with only a warning, so the reads just vanish and the job runs
on what's left. Never hand-roll a read-lib block in a new submit command — use
`internal/readspec`, which mirrors Perl
`Bio::KBase::AppService::ReadSpec`'s selection. Two independent axes:

| axis | values | Perl field |
|---|---|---|
| SRA param **name** | `srr_ids` / `srr_libs` | `srr_label` |
| SRA entry **shape** | bare string / `{srr_accession}` | `srrAlt` |

plus per-library `sample_id` (`samples`), `condition` (`rnaseq`), and
`primers`/`primer_version`/`sample_level_date` (`analysis`). Constructor rules
(`ReadSpec.pm:229-236`): `samples||analysis` → `srrAlt`;

#### Pagination is cursor-only (2026-10-14)

**Offset pagination is gone from the SDK** — PR
https://github.com/BV-BRC/BV-BRC-Go-SDK/pull/14, merged 2026-10-14 (`59554b3`).
`Query`, `QueryCallback` and `Stream` all page by `X-Cursor-Mark` through one
unexported `cursorPages` helper in `api/client.go`;
`QueryWithCursor`/`StreamWithCursor`/`QueryCallbackWithCursor` are **deprecated
aliases**, and `--cursor` is a **hidden deprecated no-op** kept only so existing
scripts keep running. Don't reintroduce a mode switch:
`TestNoCommandUsesOffsetPagination` (`internal/cliroot/`) fails the build on
`dataOpts.Cursor`, a `*WithCursor` call, a `limit(n,offset)` body, or the stale
`alpha.bv-brc.org` advice.

- **Why:** `start=N&rows=M` makes every Solr shard collect and rank `N+M` docs
  and the aggregator merge them — work proportional to the offset, repeated per
  page and discarded, paid by the shared tier. One page at offset 1,000,000 on
  `genome_feature` measured **96.7 s** (QTime 96,573 ms) vs ~5 s for a cursor
  page at any depth. It is also *less correct*: without a total order, shard
  ranking of equal docs is not stable between requests, so offset paging can
  repeat or skip rows on a static index.
- **Cursor is available everywhere** — verified on all 10 cores the SDK
  addresses × both `www.bv-brc.org/api` and `p3.theseed.org/services/data_api`
  (20/20 returned `X-Cursor-Mark`), and it is correct under a user-supplied
  **non-unique sort** (the API appends a uniqueKey tiebreaker). The old
  "requires alpha.bv-brc.org" advice was stale and is deleted.
- **The API caps a page at 25,000 rows** regardless of what `limit()` asks for,
  so `DefaultChunkSize` is already optimal — there is no page-size lever.
  `Content-Range: items <start>-<end>/<total>` gives the per-page count
  (`end-start`) and the grand total on every response.
- **The cursor mark is percent-encoded on the wire** (`api/query.go`). The API
  percent-decodes the request body and a base64 mark can contain `+`, `/`, `=`.
  Raw works today only because the decoder does not apply the form rule that
  `+` means space — not a property we control. `*` → `%2A` is accepted.
- **`q.Cursor(mark)` now actually works:** `cursorPages` starts from a
  caller-supplied mark instead of always `*`. The setter predated this and no
  loop read it. That is the hook a resumable dump needs — see
  `PLAN-go-cli-resumable-downloads.md`.
- **One user-visible change:** a query with no explicit `--sort` now comes back
  in uniqueKey order rather than Solr's internal order. Deterministic where it
  was not, but any golden-output comparison sees a one-time reordering.

Common `DataOptions` (in `internal/cli/options.go`) also include
`--max-retries`, `--verbose` (retry messages to stderr), `--sort` (prefix `-`
for descending), and `--user-agent`.

#### Resumable bulk dumps — the 12 whole-core commands (2026-10-14)

A multi-hour dump used to die whole. The ten `p3-all-*` plus
`p3-find-serology-data` / `p3-find-surveillance-data` now take **`--resume`**
(and `--state FILE`), checkpointing to a sidecar JSON next to the output so the
same command re-run continues from the last committed page. Branch
`feature/resumable-dumps` (`1949032`, `389392f`, `bf8a29b`) — **still not pushed
or merged** (re-checked 2026-10-20). Phase 1 of
`PLAN-go-cli-resumable-downloads.md`; Phase 2 (the 26 key-driven `p3-get-*`) is
not started. **It now predates the `/v2` module rename**, so its `go.mod` still
declares the unsuffixed path and every import lacks `/v2` — rebase onto `main`
before doing anything with it, or the build is against a module that no longer
exists under that name.

- **The ordering is the whole correctness argument, and it is easy to get
  backwards:** rows → `TabWriter.Flush` → `File.Sync` → checkpoint.
  `TabWriter` buffers, so a cursor mark recorded at callback time can name a
  page whose rows are still in userspace. Checkpointing first loses them
  **silently and permanently** — the mark has advanced past them, so nothing
  will ever re-fetch them. `cli.Dump.CommitPage` is the only writer of a
  checkpoint, so that ordering exists in exactly one place.
- **The reverse crash is cheap and is handled:** output longer than the
  recorded `bytes` means a page was written but never committed → truncate back
  and re-fetch it. **Shorter** → refuse; committed rows have gone missing and
  appending would leave a hole.
- **`--resume` requires `-o FILE`** (a pipe cannot be rolled back, and its
  consumer has already seen the rows), and the checkpoint carries a
  **signature** over endpoint/core/RQL/columns — resuming with a changed query
  is refused rather than interleaving two result sets. `--limit N` is charged
  against rows already written, so it means N rows *in total*.
- **The walk does not end on the last data page.** The API keeps handing back a
  fresh mark and signals exhaustion only with an **empty page**, so a complete
  dump commits one extra zero-row page. Hence `CommitPage` records the `done`
  sentinel whenever the mark fails to advance — otherwise a crash in the window
  before `Finish` would resume onto a mark that re-delivers the final page.
- **`TestEveryDataCommandSupportsResume`** (`internal/cliroot/`) is the guard,
  same family as `TestEveryCommandDeclaresAProduct`: anything streaming through
  `QueryCallback` must carry the seam or be listed in `notYetResumable` with a
  reason. That list (18 names) is also Phase 2's work queue.
- Verified live on a 121,293-row `p3-all-genomes` dump: SIGKILL after two
  committed pages → resume → **byte-identical** output, no duplicate ids;
  garbage appended past the checkpoint rolled back; completed re-run a no-op.
- Same PR: **`--timeout DURATION`** on every data command (the 30 s HTTP
  timeout was unreachable before) and `DefaultMaxRetries` **3 → 5**.
- **`p3-cursor-dump.sh`** (in `modules/`) remains the shell prototype the design
  came from; the Go path now covers the same ground for these 12 commands.

### sars2_assembly (SARS-CoV-2 assembly + ARTIC primer schemes)

Three recipes, selected by `determine_recipe` in `service-scripts/App-SARS2Assembly.pl`.
**`onecodex` is the default for *both* illumina and nanopore** (`:54-55`) and is the only
one that receives `primers` / `primer_version` (`:390-404`) — `artic-nanopore` uses a
hardcoded `nCoV-2019/V3`. "onecodex" is a recipe name, not an API: it is a local
reimplementation of One Codex's `covid19_call_variants.sh`. Chain is
`seqtk` → `minimap2` → `samtools view/sort` → **`ivar trim`** → `samtools mpileup` →
`ivar variants`/`consensus` → `mafft`. **bcftools is not used by onecodex at all** (only
by `sars2-cdc-illumina.pl`); `sars2-cdc-nanopore.pl` clips with `bamclipper.sh` + a
**BEDPE**, not ivar.

- **The primer schemes are a separate repo.** `sars2_assembly/primer-schemes/` is an
  *untracked clone* of `BV-BRC/primer-schemes`, and `Makefile:73-78` does
  `rm -rf primer-schemes && git clone … HEAD`. **A local edit there is destroyed by the
  next `make artic_schemes` — it must be pushed.** `PRIMER_SCHEMES_COMMIT_HASH = HEAD`
  pins nothing.
- **Two copies on disk.** The scratch clone, and the deployed
  `lib/Bio/P3/SARS2Assembly/primer_schemes` that the code actually reads (untracked build
  artifact, 0 tracked files). The target has no dependencies, so it only rebuilds if the
  directory is absent — `rm -rf` it to refresh. `cp -r` **dereferences** the
  `SARS-CoV-2 -> nCoV-2019` symlink, so the deployed tree has *both* as real directories
  and the manifest's `"path": "SARS-CoV-2"` resolves. Add a new version under
  `nCoV-2019/`; it appears under both after a build. The deployed copy here is routinely
  **behind** the clone.
- **Adding a scheme version needs no `sars2_assembly` change.** `primer_version` is a
  free-form string with **no enum** (`app_specs/SARS2Assembly.json:120-131`);
  `sars2-onecodex.pl:100-118` reads the version list, path and both filenames out of
  `bvbrc_manifest.json`; `rewrite-primers.pl:27` globs `V*`.
- **`$schemes->[-1]` is the default** (`sars2-onecodex.pl:113`) when no `primer_version`
  is passed — so **append order selects the default**, and inserting rather than
  appending silently keeps the old one.
- **`rewrite-primers.pl` dies if a version dir has no `.scheme.bed`** (`:30-38`, tries
  `nCoV-2019.scheme.bed` then `SARS-CoV-2.scheme.bed`), which breaks `make artic_schemes`
  for *every* version, not just the new one. Convention is 7-col `primer.bed` (with
  sequence) + 6-col `scheme.bed`. Its `ARTIC-V*.bed` output has **zero consumers**
  (`artic_bed`/`artic_reference` are exported but never called).
- **`sars2-onecodex.pl:135` discards the bed's strand column** and re-derives it from the
  primer *name*: `$x[3] =~ m/LEFT|(F$)/ ? "+" : "-"`, keeping only cols 1-4 plus score 60.
  The `(F$)` branch exists for **swift**, whose primers are named `…M1F`/`…M1R` and whose
  bed has only 4 columns. A scheme whose names defeat this regex gets trimmed on the wrong
  end, silently — hence the test that pins it.
- **The v5.4.2 spike-ins are coordinate-duplicates.** Each of the five sits at exactly the
  same start/end/strand/pool as an existing primer (alternative oligos for the same
  binding site, 1 substitution each). So **v5.3.2 and v5.4.2 present an identical set of
  trim intervals**, and a read-through test *on the reference* cannot distinguish them —
  it passes with either, or with garbage sequences, since sequences are discarded at
  `:135`. Two checks do have discriminating power: **primer sequence vs the reference at
  its own coordinates** (v5.3.2 has exactly 1 intentional mismatch, v5.4.2 exactly 6), and
  an end-to-end run **on a drifted template with an annealing model** (below).
- **The dropout test is what shows v5.4.2 doing its job**, and it needs an annealing
  model: a generator that amplifies every amplicon unconditionally cannot tell a scheme
  that binds the template from one that does not. With one, each of the five drift
  substitutions costs v5.3.2 a whole amplicon — a **307/235/198/270 bp** hole for
  amplicons 11/69/70/74, exactly the span the neighbours' inserts do not reach — and
  v5.4.2 closes every one. Under both annealing rules tried, v5.4.2's dropout set is a
  **subset** of v5.3.2's in every scenario and empty in all five single-mutation ones.
  Only amplicons 11 and 74 have **3'-proximal** substitutions (4 nt from the oligo's 3'
  end, i.e. extension-blocking); 69 and 70 are 13–21 nt in, where the real effect is Tm
  depression, so whether they count as "dropouts" depends on the model — say which model
  a claim rests on.
- **Amplicon 69's two spike-ins are alternates for two *different* mutations**, not a
  pair: `_69_RIGHT_1` answers 21710, `_69_RIGHT_2` answers 21717, and neither carries
  both. A test genome with all five substitutions at once is therefore a **chimera no
  lineage carries** — it matches no amplicon-69 oligo in *either* scheme and reports a
  false failure of v5.4.2. Use one scenario per independent mutation
  (`t/data/dropout-scenarios.tsv`); the all-at-once fixture is fine only for the
  variant-*recovery* test, which amplifies unconditionally.
- **Tests (added 2026-10, the module's first).**
  `primer-schemes/tests/validate_schemes.py` (63 checks: md5s, sequence↔coordinate with
  the intentional-mismatch set pinned *exactly*, bed structure, amplicon topology/tiling,
  the version delta, and that every manifest path exists). In `sars2_assembly`:
  `t/client-tests/primer-schemes.t` (22), `t/client-tests/primer-dropout-model.t` (40,
  hermetic — the annealing/rescue matrix, no bioinformatics tools needed),
  `t/server-tests/primer-dropout.t` (20, the holes end to end) and
  `t/server-tests/ivar-trim-roundtrip.t` (16,
  skips without minimap2/samtools/ivar). **`CLIENT_TESTS`/`SERVER_TESTS` were declared but
  nothing in `Makefile.common` consumes them** — `make test` had no rule at all until the
  targets were added; they use `$(KB_RUNTIME)/bin/perl`, since `DEPLOY_RUNTIME`
  (`/kb/runtime`) exists only in a deployment.
  **All of this is merged, not local** (re-checked 2026-10-20): the tests and the

- **…but none of it is in the working tree, which is the confusing part.**

- **Two traps found writing those tests.** `ivar trim` adds an **`XA:i:<n>` tag holding
  the matched primer's index in the bed**, which shifts whenever rows are inserted (720 of
  815 reads changed between v5.3.2 and v5.4.2) — so a scheme-equivalence assertion must
  compare **POS/CIGAR**, not whole records. And **`ivar consensus` output is not indexed by
  reference coordinate**, so diffing it positionally against the reference is meaningless

- **A generator that splits primer names on `_` positionally is wrong.** Scheme names

  zero-feature job from *failure* into *"annotated nothing"*. Validation happens before
  any side effect (no temp dir, no `makeblastdb`) so a bad name leaves nothing on disk;
  matching is exact first, then a case-fold, never a prefix. `-skip-classification`
  requires `-vtax` and restricts the sweep to that taxon's 1–14 reps instead of all 78,
  saving a flat ~11.5 s/genome at the cost of the cross-check.

### genome_annotation pipeline recipes — per-stage `condition` (and its silent-skip trap)

A recipe is `workflows/<id>/workflow.wf` (+ `name.txt`, `description.txt`), read
per `run_pipeline` call — no service restart to change one. `enumerate_recipes`
parses **every** `workflow.wf` as JSON, so a trailing comma in one recipe breaks
the whole listing. `workflow_dir` resolution is `GenomeAnnotationImpl.pm:447`.

Each stage may carry a **`condition`**: a Perl string `reval`'d in a `Safe`
compartment with **only `$genome`** bound, to the in-flight GTO
(`GenomeAnnotationImpl.pm:7669`). Truthy → run the stage, falsy → skip.

- **`run_pipeline` never checks `$@` after the `reval`.** A condition that *dies*
  yields `$ok = undef`, which reads as false — so a broken condition **silently
  skips its stage**, and the stderr line says only `Condition eval of '…' returns`.
  This is not hypothetical: `viral+`'s original vigor4 gate was
  `!(grep(...))[0]->{success}`, which throws when the LowVan event is **absent**
  (`(...)[0]` is undef, deref dies) — i.e. exactly when vigor4 was most wanted, it
  was skipped. **Always write the block form, which is total:**
  `!grep { $_->{tool_name} eq 'LowVan Annotate' && $_->{success} } @{$genome->{analysis_events}}`.
  Rule of thumb: conditions must **fail open** — every "can't tell" case should
  run the stage.
- **Guard multi-level derefs, or the condition mutates the GTO.**
  `$_->{metadata}->{x}` **autovivifies** `metadata => {}` on every event lacking
  the key (verified). Write `$_->{metadata} && $_->{metadata}->{x}`.
- The `Safe` default opmask permits what these conditions need: regex match,
  `scalar @{...}`, both EXPR and BLOCK forms of `grep`, `&&`/`||`, hash/array
  derefs. Single quotes inside the condition need no JSON escaping.
- `DEBUG_PIPELINE=<dir>` dumps each stage's input GTO.

#### Gating on what an annotator actually did (`success` + `metadata`)

The convention, established by lowvan's `annotate_by_viral_pssm-GTO.pl` and now
followed by vigor4: an annotation stage records `success` and a `metadata` hash on
its analysis event, and downstream stages gate on **that**, never on the presence
of features. A feature-shaped test cannot tell peptides an annotator called in this
run from peptides that arrived with a GenBank import.

`metadata` is `mapping<string, string>`, so **stringify every value** — and note
Perl truthiness then does the right thing on counts (`"0"` false, `"12"` true).
`success` means *did this run produce an annotation*, not *did the process exit 0*
(vigor can exit non-zero and still leave a parseable `.pep`; the rc goes in
`metadata.exit_code` — shifted, `$?` is 768 for an `exit(3)`).
`success`/`tool_version`/`metadata` are already on the `analysis_event` typedef
(`GenomeAnnotation.spec:52-61`), so adding them needs **no `make compile-typespec`**.

**`add_analysis_event` stores the caller's hashref, not a copy**
(`p3_core/lib/GenomeTypeObject.pm:1298`) — so register the event up front (features
need its id) and fill in `success`/`metadata` at the end; the write picks it up.

**Emit per-type counts always, including zeroes.** `p3x-annotate-vigor4.pl` emits
`CDS_called` / `mat_peptide_called` / `pseudogene_called` / `features_called` on
every path *except* the no-reference early exit (which records
`status => no_reference` and nothing else). A non-polyprotein reference (influenza,
rotavirus, RSV, the Bunyavirales genus dbs) legitimately calls zero peptides, and
an absent key cannot distinguish that from "the tool never reported".

**The `vipr_mat_peptide` gate (2026-08).** `p3x-annotate-mat-peptide.pl` used to
decide for itself whether to run; that moved into the recipes. Two PRs, **which
must land together** — the conditions read metadata only the patched vigor4
writes, and the patched script has dropped its own guard:
- `viral_annotation` [PR #3](https://github.com/BV-BRC/viral_annotation/pull/3),
  branch `feature/analysis-events` — vigor4 `success`/`metadata`; guard removed.
- `genome_annotation` [PR #34](https://github.com/TheSEED/genome_annotation/pull/34),
  branch `feature/analysis-events` — the recipe conditions.

In `viral+` **both clauses of the condition are load-bearing**, because exactly one
annotator ever runs: vigor4 is itself gated on lowvan *failing*, so a successful
lowvan leaves no vigor4 metadata to read and the `LowVan Annotate && success`
clause is the primary case; when lowvan failed, the `mat_peptide_called` clause
reads vigor4's count. The lowvan clause does **not** become redundant if lowvan
later reports `mat_peptide_called` — `"0"` is falsy, so a successful lowvan that
called no peptides would fall through the first clause. `viral` has no lowvan and
takes the first clause only.

**Repo gotcha:** `genome_annotation`'s `origin` is **`TheSEED/genome_annotation`**
(there is no `BV-BRC/genome_annotation`); the `bob` remote is the `olsonanl` fork
over SSH, which does not work on this host. `viral_annotation` has a single
`origin` = `BV-BRC/viral_annotation`.

### GTO taxonomy / lineage fields — where the lineage actually comes from

Three consumers agree on one preference order, and it is easy to write a comment that gets
this wrong (one in the toolkit did, corrected 2026-08-19).

**Order of preference** (`p3_core/lib/GenomeTypeObject.pm:1125-1145` `write_seed_dir`, and
its Go port `BV-BRC-Go-SDK/internal/seeddir/seeddir.go:139` `taxonomyString` — these
match): `taxonomy` as a **list** → `taxonomy` as a **string** → `ncbi_lineage`, taking
column **`[0]`** of each row. All strip a leading `cellular…` rank.

- **`ncbi_lineage` rows are `[taxon_name, taxon_id, taxon_rank]`**, so `[0]` is the name
  and the two above are right. **`p3_code/lib/GEO.pm:2715` takes `[1]`** — i.e. builds a
  list of taxids and calls it `lineage`. Don't copy that as a model.
- **`rast-create-genome --from-genbank` *does* populate `taxonomy`** — a common
  misconception, because the field lands as a **string**, so nothing ever reaches the
  `ncbi_lineage` branch and `ncbi_lineage` is genuinely absent. The script only forwards
  the file to the `create_genome_from_genbank` service method; the work happens in
  `seed_gjo/lib/GenBankToGTO.pm:356-368`, which sets **`taxonomy`** (joined `"; "`) and
  **`domain`** from the GenBank `ORGANISM` lineage block, plus `scientific_name` and
  `ncbi_taxonomy_id`. Verified on `A-California-07-2009-H1N1.{gb,gto}`: `taxonomy =
  "Viruses; Riboviria; …; Orthomyxoviridae; Alphainfluenzavirus; Alphainfluenzavirus
  influenzae"`, `domain = "Virus"`.
- Real caveats that do survive: the assignment is guarded by `if ($locus->{taxonomy})`, so
  a GenBank record with no lineage under `ORGANISM` yields nothing (rare — 0 of 300
  sampled files in `/home/mshukla/reannotation/genomes_gb`); both assignments are `||=`,
  so an existing value wins; and the value is a **string despite the field name**, which
  hand-written consumers routinely assume is a list.
- **Consequence for LowVan:** the annotation taxon can be derived from the GTO's own
  `taxonomy` field by exact-matching its `;`-separated tokens against the 34 valid names —
  no need to re-read the source `.gb`. Confirmed: the influenza GTO above yields
  `['Alphainfluenzavirus']`.
